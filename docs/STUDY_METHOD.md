# DBA 학습 방법과 루틴

목표는 많이 읽는 것이 아니라 **짧은 시간 안에 이해하고, 직접 재현하고, 기억에서 꺼낼 수 있는 상태**를 만드는 것이다.

핵심 원칙은 두 가지다.

1. **문제 → 예측 → 실험 → 원리 → 인출** 순서로 공부한다.
2. 자료와 자극을 계속 더하지 않고, **핵심 자료를 반복해서 깊게 본다.**

---

## 핵심 학습 루프

```text
문제 제시
  ↓
결과 예측 + 판단 근거 작성
  ↓
직접 실험
  ↓
상태 변화 관찰
  ↓
원리 학습
  ↓
내 예상과 실제 결과 비교
  ↓
5~10줄로 압축
  ↓
복습 질문으로 변환
  ↓
며칠 뒤 노트 없이 인출
```

DBA 공부는 책을 처음부터 끝까지 읽는 방식보다 **문제 → 실험 → 원리** 순서로 진행한다.

예시:

> PostgreSQL에서 같은 row를 반복 UPDATE하면 왜 테이블 크기가 증가할 수 있을까?

1. 결과를 먼저 예상한다.
2. **왜 그렇게 예상했는지** 적는다.
3. 직접 UPDATE를 반복한다.
4. `pg_stat_user_tables`, tuple 상태, 파일 크기 등을 확인한다.
5. MVCC, dead tuple, VACUUM, HOT을 공부한다.
6. 결과뿐 아니라 **내 판단 과정에서 어디가 맞았고 틀렸는지** 확인한다.

---

# 1. 자료를 늘리지 않는다 — 핵심 자료 반복

새로운 강의, 블로그, 책을 계속 추가하면 이해가 깊어지는 것이 아니라 **문맥 전환 비용만 증가할 수 있다.**

한 주제의 기본 자료를 제한한다.

```text
1순위 : PostgreSQL 공식 문서
2순위 : 메인 교재 1권
3순위 : 이해가 막힐 때만 보조 자료 / AI
4순위 : 직접 실험
```

원칙:

- 같은 개념을 설명하는 자료를 여러 개 수집하지 않는다.
- 이미 좋은 자료가 있다면 새로운 자료를 찾기 전에 다시 본다.
- 검색은 **구체적인 질문이 생겼을 때만** 한다.
- AI에게 처음부터 요약을 맡기지 않는다. 먼저 스스로 읽고 예상한다.

목표는 `자료 소비량`이 아니라 **핵심 자료를 얼마나 정확히 이해했는가**다.

---

# 2. 회독은 "다시 읽기"가 아니라 관점을 바꿔 반복한다

중요 개념은 한 번 보고 넘어가지 않는다.

```text
1회차 : 전체 구조와 용어 파악
2회차 : 직접 실험하고 상태 변화 확인
3회차 : 결과를 미리 예측한 뒤 다시 실험
4회차 : MySQL / 다른 개념과 비교하고 예외 확인
5회차 : 자료 없이 원리와 장애 상황 설명
```

예: MVCC

```text
1회차 : MVCC / Tuple / Snapshot 관계 이해
2회차 : xmin/xmax, UPDATE 결과 직접 확인
3회차 : 두 세션을 열고 visibility 결과 예상
4회차 : VACUUM / HOT / InnoDB MVCC와 연결
5회차 : 노트 없이 "왜 PostgreSQL UPDATE가 새 tuple을 만드는가" 설명
```

**회독 횟수 자체가 목표는 아니다.**
5회차까지 갔어도 설명하지 못하면 다시 필요한 단계로 돌아간다.

---

# 3. 정답보다 "왜 그렇게 판단했는가"를 검증한다

맞힌 문제도 복습 대상이 될 수 있다.

예를 들어 결과를 맞혔더라도:

```text
예상: Seq Scan이 발생할 것이다.
실제: Seq Scan 발생.
```

여기서 끝내지 않는다.

다시 확인한다.

- 왜 Seq Scan이라고 판단했는가?
- Planner가 실제로 사용한 비용 정보는 무엇인가?
- 데이터 분포가 달라지면 같은 판단이 유지되는가?
- Index Scan으로 바뀌는 경계는 무엇인가?

**우연히 맞힌 답은 실력이 아니다.**

공부할 때 항상 다음 세 가지를 분리한다.

```text
결과가 맞았는가?
판단 근거가 맞았는가?
다른 조건에서도 설명할 수 있는가?
```

# 4. 공부한 내용은 4가지로만 정리한다

## 4.1 개념 지도 (Concept Map)

새 개념이 전체 DB 구조에서 어디에 속하는지 파악하기 위한 지도다.

```text
PostgreSQL
├─ Storage
│  ├─ Heap / Page / Tuple
│  └─ TOAST
├─ Transaction
│  ├─ MVCC
│  ├─ Snapshot
│  └─ Isolation
├─ Recovery
│  ├─ WAL
│  ├─ Checkpoint
│  └─ PITR
├─ Performance
│  ├─ Index
│  ├─ Planner
│  └─ EXPLAIN ANALYZE
├─ Maintenance
│  ├─ VACUUM
│  ├─ Autovacuum
│  └─ ANALYZE
└─ HA
   ├─ Streaming Replication
   └─ Failover
```

개념을 배울 때마다 지도를 조금씩 확장한다. 완벽하게 만들려고 하지 않는다.

## 4.2 개념 노트 (Concept Note)

개념 하나를 **5~10줄 정도로 압축**한다.

반드시 다음 질문에 답한다.

- 한 줄로 무엇인가?
- 왜 필요한가?
- 내부 상태가 어떻게 변하는가?
- 문제가 생기면 어떤 증상이 나타나는가?
- 무엇으로 관찰할 수 있는가?
- 어떤 개념과 연결되는가?

책 내용을 그대로 옮겨 적지 않는다.

## 4.3 실험/장애 기록 (Lab / Incident Note)

DBA 학습에서 가장 중요하다.

```text
행동
↓
내부 상태 변화
↓
관찰 결과
↓
왜 그렇게 됐는가?
```

SQL 자체보다 **실행 전후의 상태 변화와 원인**을 기록한다.

가능하면 다음을 실제로 확인한다.

- `EXPLAIN (ANALYZE, BUFFERS)`
- `pg_stat_*`
- `pg_locks`
- 세션 / 트랜잭션 상태
- WAL / Checkpoint
- 파일 크기 / tuple 변화
- Replication 상태
- 로그

## 4.4 복습 질문 + 오답 (Retrieval / Mistakes)

정리한 내용을 질문으로 바꾼다.

예시:

- PostgreSQL UPDATE가 기존 tuple을 덮어쓰지 않는 이유는?
- dead tuple을 즉시 제거할 수 없는 이유는?
- 일반 VACUUM이 테이블 파일 크기를 줄이지 않는 이유는?
- HOT UPDATE가 index 갱신을 피할 수 있는 조건은?

다음 복습 때 **노트를 읽기 전에 먼저 답한다.**

틀렸다면 결과뿐 아니라 **틀린 판단 과정**을 남긴다.

```text
[착각]
VACUUM은 dead tuple을 삭제해서 파일 크기를 줄인다.

[정정]
일반 VACUUM은 공간을 재사용 가능하게 만들지만 보통 OS에 반환하지 않는다.

[왜 착각했는가]
'정리한다'는 표현을 물리적 파일 축소로 이해했다.
```

# 5. 하루 2~3시간 고강도 루틴

| 시간 | 내용 |
|---:|---|
| 20분 | 전날 복습 질문을 노트 없이 답하기 |
| 30분 | 핵심 자료 재회독 + 새로운 개념 1개 |
| 60분 | 결과를 먼저 예상하고 직접 실험 / 장애 재현 |
| 25분 | 결과와 판단 근거 분석 |
| 20분 | 개념/오답 압축 정리 + 복습 질문 작성 |
| 10분 | 아무것도 보지 않고 오늘 내용을 말로 설명 |

권장 비율:

```text
읽기 / 자료 소비      15~20%
직접 실험             35%
기억에서 꺼내기       25~30%
판단 과정 검증        15~20%
정리                   10~15%
```

**읽는 시간이 가장 길어지지 않도록 한다.**

시간이 부족한 날:

```text
복습 15분
→ 핵심 실험 30분
→ 판단 검증 10분
→ 질문 5분
```

새로운 내용을 억지로 추가하기보다 **기존 내용을 다시 정확히 인출하는 것을 우선**한다.

---

# 6. 복습 주기

새로 공부한 내용은 다음 시점에 다시 인출한다.

```text
D+1 → D+3 → D+7 → D+14 → D+30
```

- 질문을 보고 노트 없이 답한다.
- 80% 이상 정확하면 다음 주기로 넘긴다.
- 틀린 질문만 다시 공부한다.
- 맞았더라도 이유를 설명하지 못하면 틀린 것으로 본다.
- 이미 아는 내용을 처음부터 다시 읽지 않는다.

---

# 7. 주간 루틴

주 5일을 공부한다고 가정한다.

```text
월~목 : 핵심 개념 반복 + 실험
금    : 장애/성능 시나리오 종합 실습
주말  : 이번 주 질문 전체 인출 + 오답/판단 근거 정리
```

매주 최소 하나는 **실제 운영 장애 형태**로 끝낸다.

예시:

- 느린 쿼리 원인 분석
- Deadlock 재현 및 분석
- Autovacuum 지연으로 bloat 만들기
- Replication lag 발생시키기
- Backup 후 PITR 수행

주말에는 새로운 자료를 추가하기보다 이번 주 자료를 다시 본다.

---

# 8. 공부 환경은 "더하기"보다 "빼기"

집중력을 의지에 맡기지 않는다.

공부 시작 전에 환경을 고정한다.

```text
휴대폰 다른 방 / 가방에 넣기
알림 OFF
브라우저 탭 최소화
Threads / YouTube / 커뮤니티 차단
오늘 사용할 문서와 DB만 열기
정해진 시간 동안 한 주제만 진행
```

공부 중 궁금한 것이 생겨도 바로 옆길로 새지 않는다.

`나중에 확인할 질문`에 적고 현재 실험을 끝낸 뒤 확인한다.

또한 장기간 고강도 공부에서는 다음을 공부의 일부로 본다.

- 일정한 수면
- 가벼운 운동
- 과도한 카페인/야식으로 수면을 망치지 않기
- 공부 시간을 매일 비슷한 시간대로 고정

특정 음식이나 생활습관이 인지능력을 극적으로 향상시킨다고 가정하지 않는다. 목적은 **컨디션 변동과 집중 방해를 줄이는 것**이다.

---

# 9. 빠르게 익히기 위한 규칙

1. **책을 완독하는 것을 목표로 하지 않는다.** 필요한 핵심 자료를 반복한다.
2. **자료를 계속 추가하지 않는다.** 모르는 질문이 명확할 때만 검색한다.
3. **개념 하나당 최소 한 번 직접 상태를 변화시킨다.**
4. **맞힌 문제도 판단 근거가 틀렸으면 오답이다.**
5. **정리보다 인출에 시간을 더 쓴다.** 읽어서 익숙한 것과 설명할 수 있는 것은 다르다.
6. **예쁜 노트를 만들지 않는다.** 개념 노트는 5~10줄이면 충분하다.
7. **모르는 용어가 연속으로 나오면 상위 개념으로 돌아간다.** 계층을 먼저 잡는다.
8. **MySQL과 비교할 수 있는 개념은 비교한다.** 기존 경험을 새 지식의 anchor로 사용한다.
9. **장애와 실패를 일부러 만든다.** 정상 동작보다 실패 과정에서 상태 변화가 더 잘 보인다.
10. **매일 마지막에는 백지 설명을 한다.** 설명이 막히는 지점이 다음 공부 대상이다.
11. **집중력을 의지로 해결하지 않는다.** 방해 요소를 공부 시작 전에 제거한다.

# 10. AI 활용 방법

AI는 요약기가 아니라 **시험관과 실습 코치**로 사용한다.

추천 요청 방식:

```text
오늘 PostgreSQL MVCC를 공부했다.
DBA 면접 수준으로 한 문제씩 질문해줘.
내가 답하기 전에는 정답을 말하지 말고,
답변 후 결과뿐 아니라 내 판단 근거에서 틀린 부분과 빠진 핵심만 교정해줘.
```

다음날에는:

```text
어제 공부한 내용 중 내가 틀렸거나
우연히 맞혔던 개념을 중심으로 다시 시험해줘.
단순 정의보다 내부 상태 변화와 장애 상황을 물어봐줘.
```

AI에게 새로운 자료를 무한히 생성하게 하지 않는다.

목표는 AI에게 답을 받는 것이 아니라 **내 머리에서 답을 꺼내고 내 판단 과정을 검증하는 횟수를 늘리는 것**이다.

# 최종 원칙

```text
많이 읽기       < 많이 떠올리기
자료 추가        < 핵심 자료 반복
정답             < 올바른 판단 과정
예쁜 정리        < 짧은 압축
정상 동작        < 장애 재현
명령어 암기      < 내부 상태 이해
의지             < 방해 요소 제거
완독             < 문제 해결
```

DBA 공부는 **핵심 자료를 제한하고, 문제 → 예측 → 실험 → 상태 관찰 → 판단 검증 → 원리 → 인출을 반복**한다.
