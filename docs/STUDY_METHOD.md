# DBA 학습 방법과 루틴

목표는 많이 읽는 것이 아니라 **짧은 시간 안에 이해하고, 직접 재현하고, 기억에서 꺼낼 수 있는 상태**를 만드는 것이다.

## 핵심 학습 루프

```text
문제 제시
  ↓
결과 예측
  ↓
직접 실험
  ↓
상태 변화 관찰
  ↓
원리 학습
  ↓
5~10줄로 압축
  ↓
복습 질문으로 변환
  ↓
며칠 뒤 노트 없이 인출
```

DBA 공부는 책을 처음부터 끝까지 읽는 방식보다 **문제 → 실험 → 원리** 순서로 진행한다.

예시:

> PostgreSQL에서 같은 row를 반복 UPDATE하면 왜 테이블 크기가 증가할 수 있을까?

1. 결과를 먼저 예상한다.
2. 직접 UPDATE를 반복한다.
3. `pg_stat_user_tables`, tuple 상태, 파일 크기 등을 확인한다.
4. MVCC, dead tuple, VACUUM, HOT을 공부한다.
5. 결과가 왜 발생했는지 설명한다.

## 공부한 내용은 4가지로만 정리한다

### 1. 개념 지도 (Concept Map)

새 개념이 전체 DB 구조에서 어디에 속하는지 파악하기 위한 지도다.

```text
PostgreSQL
├─ Storage
│  ├─ Heap / Page / Tuple
│  └─ TOAST
├─ Transaction
│  ├─ MVCC
│  ├─ Snapshot
│  └─ Isolation
├─ Recovery
│  ├─ WAL
│  ├─ Checkpoint
│  └─ PITR
├─ Performance
│  ├─ Index
│  ├─ Planner
│  └─ EXPLAIN ANALYZE
├─ Maintenance
│  ├─ VACUUM
│  ├─ Autovacuum
│  └─ ANALYZE
└─ HA
   ├─ Streaming Replication
   └─ Failover
```

개념을 배울 때마다 지도를 조금씩 확장한다. 완벽하게 만들려고 하지 않는다.

### 2. 개념 노트 (Concept Note)

개념 하나를 **5~10줄 정도로 압축**한다.

반드시 다음 질문에 답한다.

- 한 줄로 무엇인가?
- 왜 필요한가?
- 내부 상태가 어떻게 변하는가?
- 문제가 생기면 어떤 증상이 나타나는가?
- 무엇으로 관찰할 수 있는가?
- 어떤 개념과 연결되는가?

책 내용을 그대로 옮겨 적지 않는다.

### 3. 실험/장애 기록 (Lab / Incident Note)

DBA 학습에서 가장 중요하다.

```text
행동
↓
내부 상태 변화
↓
관찰 결과
↓
왜 그렇게 됐는가?
```

SQL 자체보다 **실행 전후의 상태 변화와 원인**을 기록한다.

가능하면 다음을 실제로 확인한다.

- `EXPLAIN (ANALYZE, BUFFERS)`
- `pg_stat_*`
- `pg_locks`
- 세션 / 트랜잭션 상태
- WAL / Checkpoint
- 파일 크기 / tuple 변화
- Replication 상태
- 로그

### 4. 복습 질문 + 오답 (Retrieval / Mistakes)

정리한 내용을 질문으로 바꾼다.

예시:

- PostgreSQL UPDATE가 기존 tuple을 덮어쓰지 않는 이유는?
- dead tuple을 즉시 제거할 수 없는 이유는?
- 일반 VACUUM이 테이블 파일 크기를 줄이지 않는 이유는?
- HOT UPDATE가 index 갱신을 피할 수 있는 조건은?

다음 복습 때 **노트를 읽기 전에 먼저 답한다.**

틀렸다면 오답만 짧게 남긴다.

```text
[착각]
VACUUM은 dead tuple을 삭제해서 파일 크기를 줄인다.

[정정]
일반 VACUUM은 공간을 재사용 가능하게 만들지만 보통 OS에 반환하지 않는다.

[착각한 이유]
'정리한다'는 표현을 물리적 파일 축소로 이해했다.
```

## 하루 2~3시간 고강도 루틴

| 시간 | 내용 |
|---:|---|
| 20분 | 전날 복습 질문을 노트 없이 답하기 |
| 40분 | 새로운 개념 1~2개 학습 |
| 60분 | 직접 실험 / 장애 재현 |
| 20분 | 개념과 실험 결과 압축 정리 |
| 20분 | 복습 질문 5~10개 작성 |
| 10분 | 아무것도 보지 않고 오늘 내용을 말로 설명 |

권장 비율:

```text
읽기             20%
직접 실험         35%
기억에서 꺼내기   30%
정리              15%
```

**읽는 시간이 가장 길어지지 않도록 한다.**

시간이 부족한 날에는 `복습 15분 + 실험 30분 + 질문 10분`만 해도 된다.

## 복습 주기

새로 공부한 내용은 다음 시점에 다시 인출한다.

```text
D+1 → D+3 → D+7 → D+14 → D+30
```

- 질문을 보고 노트 없이 답한다.
- 80% 이상 정확하면 다음 주기로 넘긴다.
- 틀린 질문만 다시 공부한다.
- 이미 아는 내용을 처음부터 다시 읽지 않는다.

## 주간 루틴

주 5일을 공부한다고 가정한다.

```text
월~목 : 새 개념 + 실험
금    : 장애/성능 시나리오 종합 실습
주말  : 이번 주 질문만 빠르게 전체 인출 + 오답 정리
```

매주 최소 하나는 **실제 운영 장애 형태**로 끝낸다.

예시:

- 느린 쿼리 원인 분석
- Deadlock 재현 및 분석
- Autovacuum 지연으로 bloat 만들기
- Replication lag 발생시키기
- Backup 후 PITR 수행

## 빠르게 익히기 위한 규칙

1. **책을 완독하는 것을 목표로 하지 않는다.** 필요한 부분을 찾아 원리를 이해한다.
2. **개념 하나당 최소 한 번 직접 상태를 변화시킨다.**
3. **정리보다 인출에 시간을 더 쓴다.** 읽어서 익숙한 것과 설명할 수 있는 것은 다르다.
4. **예쁜 노트를 만들지 않는다.** 개념 노트는 5~10줄이면 충분하다.
5. **모르는 용어가 연속으로 나오면 상위 개념으로 돌아간다.** 계층을 먼저 잡는다.
6. **MySQL과 비교할 수 있는 개념은 비교한다.** 기존 경험을 새 지식의 anchor로 사용한다.
7. **장애와 실패를 일부러 만든다.** 정상 동작보다 실패 과정에서 상태 변화가 더 잘 보인다.
8. **매일 마지막에는 백지 설명을 한다.** 설명이 막히는 지점이 다음 공부 대상이다.

## AI 활용 방법

AI는 요약기가 아니라 **시험관과 실습 코치**로 사용한다.

추천 요청 방식:

```text
오늘 PostgreSQL MVCC를 공부했다.
DBA 면접 수준으로 한 문제씩 질문해줘.
내가 답하기 전에는 정답을 말하지 말고,
답변 후 틀린 부분과 빠진 핵심만 교정해줘.
```

다음날에는:

```text
어제 공부한 내용 중 내가 틀렸던 개념을 중심으로 다시 시험해줘.
단순 정의보다 내부 상태 변화와 장애 상황을 물어봐줘.
```

목표는 AI에게 답을 받는 것이 아니라 **내 머리에서 답을 꺼내는 횟수를 늘리는 것**이다.

## 최종 원칙

```text
많이 읽기 < 많이 떠올리기
예쁜 정리 < 짧은 압축
정상 동작 < 장애 재현
명령어 암기 < 내부 상태 이해
완독 < 문제 해결
```

DBA 공부는 **문제 → 예측 → 실험 → 상태 관찰 → 원리 → 인출**의 반복으로 진행한다.
